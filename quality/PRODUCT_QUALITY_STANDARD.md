# 프로그램 제품 품질 표준

문서 ID: PQS-002  
버전: 2.0.1  
상태: 최종본  
적용 방식: 완료 판정(exit gate)  
기준일: 2026-08-31

## 1. 개정 목적

이 표준은 기능을 모두 한 화면에 나열한 연구 시제품을 상용 프로그램으로 판정하는 오류를 막는다. 기능 완전성, 연구 무결성, 시각·상호작용 품질을 서로 독립적으로 검증하며 셋 중 하나라도 미달하면 `출시급` 또는 `완료`로 판정하지 않는다.

이전 PDF와 화면은 기능·수식·실행 근거를 확인하는 기준 자료이지, 화면 배치나 정보구조를 복제할 디자인 시안이 아니다. 기존 기능의 의미는 보존하되 긴 단일 페이지, 연속된 설명문, 모든 표·그래프·설정을 동시에 펼친 구조는 다시 설계해야 한다.

개발 중에는 실패 항목이 있어도 작업할 수 있다. 그러나 완료를 주장할 때는 `QUALITY_GATES.yaml`의 모든 적용 필수 게이트가 `PASS` 또는 승인된 `NOT_APPLICABLE`이어야 한다.

### 1.1 Gate 적용 범위

2.0의 최종 품질기준은 하나지만 검사 실행 범위는 작업 목적에 따라 다르다.

- `CONTINUOUS_RESEARCH`: 연구 반복에는 연구 무결성·계보·관련 검산만 항상 강제한다. 제품 UI·배포 미완료는 연구를 막지 않고 품질 부채로 기록한다.
- `CHANGE_INTEGRATION`: 프로그램에 합치는 변경에는 변경 영향 gate만 실행한다. 영향받지 않은 전체 gate를 매번 재실행하지 않는다.
- `PRODUCT_EXIT`: 프로그램 전체 완료·출시급·상용 수준·배포 가능을 주장할 때 QG-00~QG-12 전체를 실행한다.

이 구분은 품질 등급이나 승격 단계가 아니다. 같은 최종 기준에서 검사 시점과 범위만 정한다. 사용자가 별도로 승격을 지시할 필요가 없으며 Codex가 요청 범위로 profile을 판정·기록한다. 연구 무결성, 실행 혼합, 데이터 손상, 허위 주장 BLOCKER는 모든 profile에서 항상 강제한다.

## 2. 기존 운영체계와의 관계

1. 기존 상태·결정·변경·실험·체크포인트 기록을 삭제하거나 대체하지 않는다.
2. 이 표준은 기존 운영체계 위에 추가되는 완료 판정 규칙이다.
3. 현재 연구내용은 저장소의 최신 승인 상태와 모델 계약에서 읽는다. 과거 PDF를 최신 연구 상태로 간주하지 않는다.
4. 품질을 맞추려고 원시 결과, 실패 기록, 수학식, golden fixture를 근거 없이 바꾸지 않는다.
5. UI 재설계는 과학적 의미를 바꾸지 않으며, 과학적 변경은 별도 연구 결정으로 기록한다.

## 3. 반드시 구분할 두 층

### 3.1 보존해야 하는 의미 계약

- 실행 ID와 실행별 입력 스냅샷
- 현재 결과 조건과 다음 실행 조건의 분리
- seed, H, population, 세대, 실제 NFE, 준비시간과 진화시간
- 목적함수, 제약, 자원 규칙, representation/operator 의미
- 0세대 주입과 진화 개선의 구분
- LP 하한, MILP feasible 해·dual bound, 관측 최저, 전역 최적성의 구분
- 생존 집단, 전체 평가행, 누적 archive, best-known set의 구분
- 수동 해 선택과 동일 배치 ID의 지도·그래프·표·다운로드 연결
- 기본 공간 표본과 추가 격자 검산 상태
- 저장·중단·복구 한계와 원시 근거

### 3.2 자유롭게 다시 설계해야 하는 표현 계약

- 페이지와 메뉴의 수 및 순서
- 카드, 표, 탭, 패널, drawer, dialog 사용 방식
- 화면 밀도와 설명문의 위치
- 지도·그래프·목록 배치
- 색상, 타이포그래피, 간격, 아이콘, 모션
- 설정 입력 방식과 단계화

의미 계약을 지킨다는 이유로 과거 PDF의 세로 순서와 구성요소 배치를 그대로 유지해서는 안 된다.

## 4. 상용 프로그램급 UI의 정의

상용 프로그램급 UI는 단순히 둥근 카드와 색상을 적용한 화면이 아니다. 다음 조건을 모두 만족해야 한다.

1. 사용자의 핵심 작업을 기준으로 화면이 나뉜다.
2. 첫 화면에서 현재 상태와 다음 행동을 즉시 파악할 수 있다.
3. 한 화면에 하나의 주 작업과 하나의 우선 행동이 있다.
4. 지도·차트·결과 등 핵심 작업공간이 가장 넓고 높은 시각 우선순위를 갖는다.
5. 고급 설정과 연구 설명은 문맥 패널, inspector, drawer, 도움말로 단계적으로 공개한다.
6. 같은 정보가 여러 카드에 중복되지 않는다.
7. 전체 기능을 보이기 위해 긴 페이지를 스크롤하도록 강요하지 않는다.
8. 로딩·빈 상태·실패·중단·완료·부분 결과가 제품 상태로 설계되어 있다.
9. 데모 데이터가 아니라 실제 실행 상태와 상호작용한다.
10. 자동 시험 외에 실제 브라우저 화면과 대표 사용자 과업으로 검증한다.

## 5. 필수 디자인 조사

중대한 UI 추가·재설계 전에 Codex는 현재 프로그램과 최신 연구 상태를 조사하고 `UI_REFERENCE_BRIEF.md`를 만든다. 이 문서는 구현 목록이 아니라 디자인 판단의 근거다.

### 5.1 현재 상태 조사

- 실행 중인 모든 주요 화면을 지원 해상도에서 캡처한다.
- 각 화면의 사용자 목적, 주 행동, 핵심 정보, 오류 가능성, 과도한 밀도, 중복을 기록한다.
- 최신 상태·결정·모델 계약을 읽고 현재 센서, 목적, 제약, 비교 지표, 증거 구조를 추출한다.
- PDF와 현재 코드가 다르면 최신 승인 연구기록을 우선하고 차이를 기록한다.

### 5.2 외부 참조 조사

대규모 UI 변경마다 최소 6개 최신 참조를 조사한다.

- 엔터프라이즈 작업공간 2개 이상
- 과학·데이터 분석 제품 2개 이상
- 지도·공간 작업공간 1개 이상
- 접근성 또는 공인 디자인 시스템 1개 이상

각 참조에는 URL, 제품/시스템명, 조사일, 적용할 패턴, 적용하지 않을 패턴, 저작권·라이선스 주의를 기록한다. 화면을 그대로 복제하지 않고 구조·상호작용 원칙을 추출한다. 90일이 지난 참조 조사로 중대한 UI 완료 판정을 해서는 안 된다.

기본 조사 출발점은 다음과 같다. Codex는 이를 고정 정답으로 쓰지 말고 조사 시점의 최신 공식 문서를 다시 확인한다.

- Atlassian Design System Layout: https://atlassian.design/components/navigation-system/layout
- IBM Carbon Dashboards: https://carbondesignsystem.com/data-visualization/dashboards/
- IBM Carbon Chart Types: https://carbondesignsystem.com/data-visualization/chart-types/
- Esri Calcite Workspace Application: https://developers.arcgis.com/calcite-design-system/sample-code/app-workspace-application/
- Esri Calcite Shell: https://developers.arcgis.com/calcite-design-system/components/shell/
- W3C WCAG: https://www.w3.org/WAI/standards-guidelines/wcag/
- W3C Complex Images: https://www.w3.org/WAI/tutorials/images/complex/

### 5.3 제공된 UI 참조에서 추출할 원칙

사용자가 제공한 CANAPE, Jira, Cafe24 계열 화면은 다음 구조 원칙의 참조다.

- 고정 앱 셸과 명확한 전역 탐색
- 현재 위치가 보이는 선택 상태
- 화면 제목, 문맥, 주 행동의 일관된 상단 영역
- 카드형 갤러리는 실제 개체 목록에만 사용
- 고밀도 비교는 정렬·검색·필터가 있는 표로 처리
- 설정은 별도 화면 또는 문맥 패널로 분리
- 빈 상태는 짧은 설명과 다음 행동을 제공
- 보조 행동은 더보기 메뉴에 두되 핵심 행동은 숨기지 않음
- 충분한 여백과 정렬, 반복 가능한 행·열 체계

이 참조들의 파란색, 보라색, 로고, 세부 컴포넌트를 복제하는 것이 목표가 아니다.

## 6. NSGA-III 프로그램의 권장 제품 정보구조

아래는 기본 방향이다. 더 나은 구조가 조사·사용성 근거로 입증되면 변경할 수 있다.

### 6.1 실행 대시보드

목적: 저장된 실행의 상태를 보고 새 실험 또는 기존 분석으로 진입한다.

- 최근 실행, 완료·중단·실패 상태, 핵심 조건, 수정 시각
- 검색·필터·정렬 및 목록/카드 전환
- 명확한 `새 실험` 주 행동
- 실행 삭제·내보내기 같은 보조 행동은 행 메뉴
- 빈 상태에서는 첫 실험 생성 안내

### 6.2 실험 설정

목적: 다음 계산의 조건을 이해하고 검증한 뒤 실행한다.

- 성능 기준·평가영역
- 센서·자원
- 목적·제약
- 알고리즘·초기화
- 실행 전 요약과 validation

모든 입력을 한 번에 펼치지 않는다. 단계, 탭, accordion 또는 좌측 설정 목록을 사용한다. 현재 저장 실행과 변경된 다음 입력의 차이는 요약 영역에서 비교한다.

### 6.3 실행 모니터

목적: 실행 상태를 감시하고 안전하게 중단·복구 행동을 한다.

- 진행률, 현재 세대, NFE, 경과시간, 준비/진화 구분
- 현재 상태와 종료 사유
- 핵심 추이 그래프 1~2개
- 로그와 고급 진단은 보조 패널
- 중단은 명확하되 오조작 방지

### 6.4 해 탐색 작업공간

목적: 사용자가 해를 직접 선택하고 공간·목적·자원 trade-off를 이해한다.

- 지도 또는 핵심 시각화를 주 캔버스로 사용
- 왼쪽/하단: 필터 가능한 해 목록 또는 Pareto plot
- 오른쪽: 선택 해 inspector
- 세대 선택과 현재 실행 문맥은 고정 표시
- 목록·plot·지도·inspector의 선택을 양방향 연결
- 해 미선택 시 0값을 만들지 않고 의도적인 빈 상태 표시

### 6.5 비교·근거

목적: 실행·세대·해를 비교하고 연구 근거를 검증·내보낸다.

- 비교 바구니 또는 고정 선택 2~4개
- 조건 차이, 목적값, 제약, 자원, NFE, 시간, seed, 코드 revision
- LP/MILP/Greedy 근거와 주장 한계를 별도 섹션으로 표시
- 원시 결과·manifest·검증 근거 다운로드
- dense comparison은 표, 경향은 차트, 공간 차이는 지도 small multiples 사용

### 6.6 방법·가정 도움말

수식, 비용 가정, representation/operator 설명, 최적성 한계는 별도 방법 화면 또는 문맥 도움말에서 제공한다. 분석 화면 본문에 장문의 교재를 삽입하지 않는다.

## 7. 최신 연구를 흡수하는 UI 구조

새 센서·목적함수·제약·알고리즘이 추가될 때마다 카드와 섹션을 계속 붙이는 방식은 금지한다.

- 연구 모델과 UI 표시를 schema/metadata 기반으로 연결한다.
- 센서·목적·제약은 이름, 단위, 방향, 설명, 상태, 출처를 가진 공통 모델로 렌더링한다.
- 기본 화면은 핵심 3~7개 지표만 보이고 전체 지표는 사용자 선택·열 구성·상세 패널로 제공한다.
- 새 연구 요소는 기존 탐색·비교·필터 구조에 들어가야 한다.
- 실험 스키마 버전과 UI 지원 버전을 확인하고 모르는 필드는 경고 없이 버리지 않는다.
- 연구 상태가 바뀌면 `UI_REFERENCE_BRIEF.md`의 콘텐츠 인벤토리와 화면 매핑을 갱신한다.
- 연구 개념이 늘어도 전역 탐색 메뉴 수를 무한히 늘리지 않는다.

## 8. 시각 시스템 기준

### 8.1 디자인 토큰

색상, 타이포그래피, 간격, radius, elevation, border, icon 크기, motion duration을 토큰으로 관리한다. 임의 값과 화면별 예외를 누적하지 않는다.

### 8.2 계층과 밀도

- 화면 제목, 상태, 주 행동이 첫 viewport에 있다.
- 핵심 캔버스/결과가 화면 면적의 중심을 차지한다.
- 설명문보다 데이터와 행동을 우선한다.
- 카드 안에 다시 카드가 반복되는 과도한 container nesting을 피한다.
- 동일 중요도의 요소는 동일한 크기·스타일을 쓴다.
- 표는 행 높이, 정렬, sticky header, 단위 표시를 일관되게 한다.

### 8.3 색상과 상태

센서 종류, 목표 상태, 선택 상태, 오류 상태의 색을 구분한다. 같은 의미에는 같은 색을 쓰고 색만으로 정보를 전달하지 않는다. 데이터 palette와 UI action palette를 구분한다.

### 8.4 차트·지도

- 차트는 질문에 맞는 유형을 선택한다. 단순히 구현 가능한 chart를 사용하지 않는다.
- 동일 데이터에 축·단위·범례·색상 의미가 일관된다.
- filter, zoom, 세대, 해 선택이 연결된 view에 동기화된다.
- 선택 해는 다른 해와 명확히 구분하되 비선택 데이터도 읽을 수 있다.
- tooltip 외에 정확한 값에 접근할 표 또는 inspector가 있다.
- 지도·차트에는 요약 설명과 접근 가능한 대체 표현을 제공한다.

### 8.5 상호작용

- 주 행동은 화면마다 하나를 우선한다.
- 위험 행동은 확인과 복구 가능성을 고려한다.
- 모든 interactive element에 hover, focus, active, disabled, loading 상태가 있다.
- 150ms 이상 응답은 즉각적인 상태 피드백을 제공하고 긴 계산은 취소 가능성을 표시한다.
- selection, filter, sort, zoom, 열 구성이 화면 이동 후에도 예측 가능하게 유지된다.

## 9. 금지되는 UI 안티패턴

다음 중 하나라도 핵심 화면에 남으면 QG-06은 `FAIL`이다.

- PDF 목차 순서대로 모든 내용을 한 페이지에 쌓기
- 내부 모듈·데이터 구조 이름을 그대로 메뉴로 만들기
- 구성요소마다 카드 하나씩 만들기
- 모든 설명·수식·주의문을 기본 화면에 상시 노출하기
- 주요 작업이 여러 화면 아래쪽에 흩어져 있는 구조
- 첫 viewport 대부분을 설정 폼이나 장문으로 채우기
- 동일 실행 상태를 서로 다른 컴포넌트에서 다르게 표시하기
- 데모 placeholder 또는 정적 차트를 실제 결과처럼 보이게 하기
- 디자인 시스템 없이 임의 색·간격·아이콘을 화면마다 추가하기
- 사용자가 해를 고르지 않았는데 프로그램이 대표해를 자동 선택하기
- 기능이 존재한다는 이유만으로 발견 가능성과 사용성을 통과 처리하기

## 10. 측정 가능한 UI 완료 기준

중대한 UI 변경은 다음을 모두 만족해야 한다.

1. 최신 `UI_REFERENCE_BRIEF.md`가 있다.
2. 최소 2개의 구조 대안을 비교하고 선택 이유를 기록했다.
3. 핵심 5개 과업의 interactive prototype 또는 실제 구현을 검증했다.
4. 대표 사용자 5명 이상 또는 사용자 승인 대체 평가에서 핵심 과업 성공률 90% 이상, 치명적 오조작 0건이다.
5. 사용성 평가가 불가능한 경우 전문 휴리스틱 검토와 사용자 승인 없이는 `출시급`이라 할 수 없다.
6. 1920×1080, 1440×900, 1280×720에서 주요 화면을 직접 캡처·검토했다.
7. 200% 확대에서 정보 손실과 필수 가로 스크롤이 없다. 데이터 캔버스의 예외는 동등한 대체 view가 있어야 한다.
8. WCAG 2.2 AA를 목표로 자동·수동 접근성 검사를 통과했다.
9. screenshot regression 또는 동등한 시각 회귀 증거가 있다.
10. 첫 viewport에서 화면 목적, 현재 상태, 주 행동, 핵심 결과를 식별할 수 있다.
11. UI 전문가 또는 사용자 승인자가 실제 화면을 보고 `문서형 시제품`이 아님을 승인했다.

## 11. 연구 무결성 기준

시각 고도화로 다음을 숨기거나 약화하면 안 된다.

- 휴리스틱 종료는 전역 최적성 인증이 아니다.
- LP 하한, MILP dual bound, feasible upper bound, 관측 최저는 명확히 구분한다.
- seed 동일성이 시간 제한 솔버의 비트 단위 재현성을 보장하지 않는다.
- 준비 평가·시간과 진화 NFE·시간을 분리한다.
- 0세대 주입 성능을 진화가 발견한 개선으로 표시하지 않는다.
- 500m 결과와 250m 검산 상태를 구분한다.
- 없는 값, 미선택, 미실행을 0 또는 성공으로 표시하지 않는다.

이 정보는 항상 화면을 가득 채울 필요는 없지만 상태 badge, 요약, inspector, 도움말, 근거 화면을 통해 해당 결과에서 즉시 접근 가능해야 한다.

## 12. 증거와 판정

좋은 증거는 대상 revision, 실행 방법, 기대값, 실제값, 화면 캡처, 사용자 과업 결과, 원시 로그를 연결한다. Codex의 서술만 있는 `깔끔해졌다`, 오래된 screenshot, 구성요소 존재 목록은 통과 증거가 아니다.

보고서는 `QUALITY_REPORT.schema.json`을 만족해야 하며 특히 `design_evidence`를 포함한다. UI에 영향이 없다고 판정하면 이유와 변경 영향 분석이 있어야 한다.

필수 게이트에 `FAIL`, `NOT_RUN`, `BLOCKED`가 하나라도 있거나 미해결 BLOCKER/MAJOR가 있으면 완료가 아니다.

## 13. 버전 1.0에서 2.0으로의 변경

- PDF의 화면 구성을 보존 대상으로 오해하지 않도록 의미/표현 계약을 분리했다.
- 최신 외부 참조 조사와 `UI_REFERENCE_BRIEF.md`를 필수화했다.
- NSGA-III 작업공간의 권장 정보구조를 정의했다.
- 기능 나열형·문서형 UI 안티패턴을 완료 차단 조건으로 추가했다.
- 디자인 대안, prototype, 사용자 과업, 실제 screenshot 검토를 필수 증거로 추가했다.
- 최신 연구가 늘어도 UI가 비대해지지 않는 schema 기반 확장 규칙을 추가했다.
